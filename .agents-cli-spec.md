# Collaborative Post Agent Spec

## Overview

Build a local agents-cli prototype using Python ADK's graph-based Workflow API. A Writer creates a post from the user's idea, and an Editor reviews it. The Writer revises from that feedback until the Editor is satisfied or the workflow reaches a hard limit of three review rounds.

The post should be approximately 300 characters. The workflow will target 280–320 characters while favoring clarity over padding. The user-facing result will contain only the final post.

## Architecture & Sub-Agents

- `Writer`: creates the first draft, then revises the current draft using the Editor's latest feedback.
- `Editor`: checks fidelity to the idea, clarity, tone, grammar, approximate length, and very simple plain language. It rejects jargon, difficult words, abstract phrasing, and complex sentences, then suggests specific simpler wording. It either provides actionable feedback or signals that the post is approved.
- ADK `Workflow`: connects initialization, Writer, Editor, review-gate, and final-output nodes as a graph. Conditional `revise` and `finish` routes implement the feedback cycle.
- A deterministic review-gate node tracks review rounds in session state, routes approved drafts to the final output, and forces completion after the third review.
- A deterministic final-output node returns only the latest post to the user.

## Example Use Cases

Input: `Share the idea that consistency beats occasional bursts of motivation.`

Expected behavior: produce a draft, review it, revise when needed, stop after approval or three Editor reviews, and return one polished post of roughly 300 characters.

Input: `Announce that our neighborhood garden is looking for Saturday volunteers.`

Expected behavior: preserve the requested announcement and call to action without inventing dates, locations, or contact details.

## Tools Required

No external APIs, retrieval systems, or custom tools are required. The agents use Gemini through ADK and coordinate through ADK session state. Local execution uses standard Google credentials supported by the agents-cli scaffold.

## Constraints & Safety Rules

- Preserve the meaning and factual content of the user's idea.
- Do not invent facts, quotations, links, statistics, dates, or calls to action absent from the idea.
- Target 280–320 characters; text outside that range is acceptable only when staying in range would harm meaning or readability.
- Count all visible characters, including spaces and punctuation.
- Editor feedback must be specific and actionable.
- Plain language is required: use common everyday words, short direct sentences, active voice, and concrete wording.
- The Editor must reject jargon, buzzwords, unexplained technical terms, difficult or uncommon words, abstract phrases, and complex sentence structures.
- Stop immediately when the Editor approves; otherwise stop after the third Editor review.
- Return the latest draft if the three-round cap is reached.
- The final user-facing response contains only the post, with no critique, labels, or process notes.

## Success Criteria

- In evaluation, 100% of core cases produce a final post after no more than three Editor reviews.
- At least 90% of evaluated final posts contain 280–320 visible characters.
- Every final post preserves the supplied idea without unsupported factual additions, judged by the evaluation rubric.
- Every final post is understandable to a non-expert on the first read and avoids jargon or difficult wording, judged by the evaluation rubric.
- Every revision after a non-approval addresses at least one specific Editor concern, judged from the generated trace.
- Approved drafts terminate the loop without another Writer revision.
- When `LOG_AGENT_CONTENT=true`, each run emits paired `agent_idea` and
  `agent_final_response` structured logs with the same request ID.

## Reference Samples

No core recipe directly matches this bounded Writer/Editor loop. The implementation uses the ADK 2.0 graph Workflow API documented in the agents-cli ADK code reference rather than cloning an unrelated recipe.

## Assumptions

- The agent is deployed directly to an authenticated Cloud Run service in `us-east1`; no CI/CD pipeline is configured.
- Sessions remain in memory and may be lost when Cloud Run instances restart or scale to zero.
- No durable or cross-session memory is needed.
- No external data source or user-specific authentication is needed beyond Google Cloud credentials.
- The generated scaffold's model setting will be preserved unless agents-cli requires choosing one during project creation.
